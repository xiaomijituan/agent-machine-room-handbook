## 本机实测记录

采集：2026-10-07，作者的 Windows 机器。工具 `curl`，同一个 URL（`left-pad`，很小的一份包元数据）：

| 目标                     | 串行三次              | 并发三个                  |
| ------------------------ | --------------------- | ------------------------- |
| `registry.npmjs.org`     | 2.01 / 1.05 / 0.94 秒 | 0.96 / 1.29 / **2.55** 秒 |
| `registry.npmmirror.com` | 0.047 ～ 0.081 秒     | 0.073 ～ 0.081 秒         |

## 一条被实测推翻的猜测

先前准备写进正文的判断是"多个 AI 代理会挤同一个出口，导致互相拖慢"。**实测不支持这一句**：并发最长 2.55 秒，串行最长也有 2.01 秒，差值落在单次抖动的范围内。所以"互相拖慢"没有写进正文，正文只留"官方源慢且抖、镜像快且稳"。

## 纠正一条过时的记录

我们的旧笔记写着"npm 官方源直连不通，必须走镜像"。**这次六次请求全部 `http=200`，直连是通的**，只是慢。同一时间测本机代理端口 `127.0.0.1:7897`：**没有进程监听**，走该端口访问 github 得到 `http=000`。

结论：本机的网络状态会变。**"通不通"这类话必须当场测量，不能引用记录。**

## 没测到什么

- **实际安装一次依赖**（几百个请求、几十兆数据）时官方源和镜像的差距怎么变：只测了一个小文件的一次请求。
- **打开代理之后的并发行为**：这次代理没有开启。
- **第一、第二两种故障在真实代码仓库里的样子**：剧本里演的是浓缩版，真实仓库里更麻烦的形态是两个改动互相看不见、合并时冲突。
- **第四、第五两种故障**：只有描述，没有实验。
- **配图本身未做可读性实测**：配图里的文字在真实手机屏幕上会不会过小、会不会互相遮挡，没有在真机上逐项量过，只核对过配图文字与正文内容一致。

## 证据等级

网络那条：**A 级**（本机真实执行、原始输出留档、限制写清），但样本极小。
剧本里的第一、第二两种故障：**B 级**（模拟器里成立，不等于真实代码里成立）。
第三种故障：**A 级**——依据不是台词而是实现，派发规则写在模拟器的代码里并带了单元测试，
这两样都在聚变仓库，任何人都能在本机跑一遍；本章没有另外补一次派发实验。
第四、第五两种故障：**C 级**（经验描述，无实验）。
