## 本机实测记录

采集：2026-10-07，作者的 Windows 机器。工具 `curl`，同一个 URL（`left-pad`，很小的一份包元数据）：

| 目标                     | 串行三次              | 并发三个                  |
| ------------------------ | --------------------- | ------------------------- |
| `registry.npmjs.org`     | 2.01 / 1.05 / 0.94 秒 | 0.96 / 1.29 / **2.55** 秒 |
| `registry.npmmirror.com` | 0.047 ～ 0.081 秒     | 0.073 ～ 0.081 秒         |

原始输出在 `evidence/registry-fetch-timing.md`。

## 测出来推翻我自己猜测的一条

我原本要写"多个 AI 会挤同一个出口，导致互相拖慢"。**实测不支持这句话**：并发最长 2.55 秒，串行最长也有 2.01 秒，这点差落在单次抖动里。所以那句话被删掉了，正文只留"官方源慢且抖、镜像快且稳"。

## 顺带纠正一条过时的记录

我们的旧笔记写着"npm 官方源直连不通，必须走镜像"。**这次六次请求全部 `http=200`，直连是通的**，只是慢。同一时间测本机代理端口 `127.0.0.1:7897`：**没有进程监听**，走它访问 github 得到 `http=000`。

结论：这台机器的网络状态会变。**"通不通"这类话必须现量，不能引用记录。**

## 没测到什么

- **真实装一次依赖**（几百个请求、几十兆）时官方源和镜像的差距怎么变。只测了一个小文件的一次请求。
- **打开代理之后**并发行为。这次代理没开。
- **乱子一、乱子二在真实代码仓库里的样子**。剧本里演的是浓缩版，真仓库里可能是"两个改动互相看不见、合并时冲突"这种更麻烦的形态。
- **乱子四、乱子五**只是描述，没做实验。
