# 第 4 章 · AI 说它做完了，我怎么知道它真做了什么

**先给一句能动手的话**：AI 交回来一句"已完成，测试全绿"，你只要三样东西——**改了哪些文件、跑了哪条命令、那条命令打印了什么**。三样缺一样，就当没做完。

这一章教的是"读输出"这件事本身。读的输出如果只有结论，那是没有输出的。

## 那一时刻

你说"把登录那块改一下，测试别挂"。二十分钟后 AI 回你：**"改完了，测试全部通过。"**

你手上现在只有一个信息：它说通过了。**没有一条命令的输出，没有一份文件清单。**

这时候有两条路。一条是信，合进去，等它晚上自己炸。另一条是要证据。这一章教你怎么要、怎么读、以及怎么不被自己的想当然骗。

## 要证据的三件套

一句话就能要：

```
把这三样给我：
1) 改了哪几个文件，每个文件改了什么（一句话一个文件）
2) 你跑了哪条命令
3) 那条命令的完整输出，末行的统计数字要看得见
```

**为什么第 3 条要"完整"**：只贴末行"12 passed"不够。末行可以由任何一条命令产生，包括跑错目标的那一条。要看得见它跑的是哪些文件、几个用例。

## 读证据的时候，先找不一致

模拟器里那一幕是这样的：AI 贴了输出，末行写"12 个用例通过"，可它前面说改了**两个**文件，输出里只出现**一个**文件名；用例总数跟仓库里的测试文件数量也对不上。

**这种不一致是最有价值的信号**。三个数字对不上，比"它明确说自己失败了"还值得停下来。

排查顺序建议这样：

1. **先核对文件清单**（`git status` 或 `git diff --name-only`）。文件都不对，后面的输出别看。
2. **自己重跑那条命令**。这条最便宜，也最可靠。
3. 数字仍然对不上，别合。这不是"AI 粗心"的问题，是你不知道它跑的是什么。

## 一个真实的教训：我读错过一行警告

这一章最该被读者记住的不是 AI，是我自己。

我们这台 Windows 机器上，提交文件时会打出这句话：

```
warning: LF will be replaced by CRLF in crlf-demo.txt.
The file will have its original line endings in your working directory
```

看到"会被换成 CRLF"，我的第一反应是：**"我这台机器上的文件都是 Windows 换行符了。"**

**这句推断是错的。** 查这个文件自己的行尾：

```
$ git ls-files --eol crlf-demo.txt
i/lf    w/lf    attr/                   crlf-demo.txt
```

工作区里这个文件**仍然是 LF**，仓库里也是 LF。第二行警告其实已经把话说清了："你工作区里保持原样"。

更打脸的是同一个仓库、同一台机器、同一个设置下，三个文件的行尾并不一样：

```
$ git ls-files --eol -- AGENTS.md CONTEXT.md README.md
i/lf    w/crlf  attr/                   AGENTS.md
i/lf    w/lf    attr/                   CONTEXT.md
i/lf    w/lf    attr/                   README.md
```

**`AGENTS.md` 的工作区是 CRLF，另外两个是 LF。** 所以"我这台机器都是 CRLF"这句话，被同一台机器上的输出直接否掉了。

**这一条对读 AI 证据有什么用**：如果我不查那个文件的真实行尾，我就会把一个不存在的问题写给 AI，让它去"修一个不是问题的东西"。**读别人的输出之前，先确认你引用的那句话到底在说什么。**

## 行尾这个坑什么时候会咬你

把日志或文件内容复制给 AI 的时候，行尾不一致会造成三件看起来像 AI 出错的事：

1. AI 按行匹配文本，带着回车的行匹配不上
2. shell 脚本带着回车在 Linux 上跑，报 `bad interpreter: /bin/bash^M`
3. 两份"内容一样"的文件，diff 显示每一行都不同

**这三种都不是 AI 的锅。** 判法只有一条：先查文件真实行尾（`git ls-files --eol <文件>`），再决定怀疑谁。

上面第 2、3 条我们在别处见过、这次**没有在本机复现**，所以只列现象，不当结论用。

## 怎么让"带证据交付"变成默认

在派活那句话里就写清验收方式。这一句直接抄去用：

```
改完后给我：改动的文件清单、你跑的命令、该命令的完整输出。
把完整输出同时写进 build.log，并告诉我文件路径。
```

**为什么要写进文件**：贴在回复里的输出会被截、会被复制时丢行。落到文件里，你随时能自己再看一遍，AI 也不能事后改口径。

模拟器里那一局就是这么派的（见 `reference.jsonl`）。

## 你自己怎么验

玩本章剧本（`scenario.json`），三个卡点依次是：只有结论没有证据 / 贴了输出但数字不一致 / 空屏可以要求带日志重跑。

**故意先选一次"信它，直接合进去"**，再选一次"要三样证据"，导出两份记录跟书里那份 `reference.jsonl` 并排比，看第一个差别落在第几步。**是比对，不是打分。**
