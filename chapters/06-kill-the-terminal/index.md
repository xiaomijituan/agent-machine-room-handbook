# 第 6 章 · 终端窗口关掉了，正在跑的活会不会死

© 2026 xiaomijituan · 正文 CC BY 4.0，代码与数据 MIT · 原仓库 https://github.com/xiaomijituan/agent-machine-room-handbook

> 这一章只回答一个问题：**你关掉的终端窗口，到底是不是进程的命根子。**
> 四条结论里三条是量出来的（其中前台那条换了第二台机器才量到），第四条写得很短，因为没量到。

## 先说清楚"关掉终端"关掉了什么

终端窗口关掉时，内核会给终端的前台进程组发一个挂起信号，很多程序就此结束。
程序要不要跟着死，取决于进程的父亲是谁、进程有没有被从终端的会话里摘出去。

一句话记法：**进程认的是"我爹是谁"，不认"窗口开不开"。**

这一章的关键就一句话：进程只认父亲是谁，不认窗口开不开。下面这张图要看的是每一格右边那一句——
同一个终端被掐掉，三格的结果并不一样。

![三种起法各自的上级进程是谁：屏一前台直跑，进程的父亲是终端会话，窗口关掉时这个终端的前台进程组会收到挂起信号，很多程序就此结束，这一格在第二台机器上量到了——日志停在第 4 行、进程变成僵尸；屏二用 nohup 加 disown 起的进程，父进程是 1 号，原来那个 shell 退出之后日志从 13 行涨到 21 行；屏三跑在 tmux 会话里的进程，宿主是 tmux 自己那个不属于任何终端的进程，伪终端被掐断之后会话仍在、日志从 6 行涨到 23 行。图底三条：关掉终端窗口打的是窗口不是进程的父亲；反过来 tmux kill-server 一下所有会话一起没了；断网的情况本章没有测](assets/three-screens-three-fathers.svg)

## 量到的第一条：分离出去的进程活着

在一台 Linux 实验机上跑一个每秒钟往日志里写一行的循环，用 `nohup` 起、再 `disown` 把循环
从当前 shell 的任务表里摘掉，然后**让启动循环的 shell 真的退出**（这台机器上每条命令都由一个
独立 shell 执行、执行完就退出，所以"换一条命令"就等于换了一个 shell）。

结果：日志行数从 13 涨到 21，进程还在，`ps -ef` 显示循环进程的上级进程编号已经是 1。

```
13 /data/proof/ticks.log   ← 起完之后 6 秒
21 /data/proof/ticks.log   ← 换一个 shell、再等 8 秒
root 176 1 ... sh -c for i in $(seq 1 120); do echo "tick $i ..." >> /data/proof/ticks.log; sleep 1; done
       ↑   ↑
     进程号  父进程已经是 1
```

这条可以直接搬到你自己的机房里：**把一个长活交给 agent 时，别把长活挂在你 ssh 进去的终端上。**

## 量到的第二条：tmux 会话也活着，但要看清你是掐断了谁

同一台机器上建一个分离的 tmux 会话跑同样的循环，然后用一个假终端连进去看一眼，3 秒后掐断假终端
（`timeout` 到点杀掉，退出码 124——**这是故意掐断，不是失败**）。

结果：会话还在（`tmux ls` 仍是同一条会话、同一个创建时间），日志从 6 行涨到 23 行；
直到我主动执行 `tmux kill-server`，会话才消失。

所以 tmux 给你的不是"进程变强了"，是**多了一层不属于任何终端的宿主**：窗口关掉只是没人看着
tmux 会话，宿主还在跑。你真正需要小心的是反过来的那一步——`kill-server` 一下，所有会话一起没了。

## 量到的第三条：前台直跑那一格，这次抓到了现场

前两格是在云端那台 Linux 实验机上量的，**那台机器没有 sshd、不能被连进来**，所以"关掉窗口"这一步
只能用 `script` 造的伪终端代替。第三格换了一台能连进来的机器：一台阿里云 ECS（CentOS 8，2 核 2G，
`sshd` 在，`tmux` 没装），进出的通道是厂商自带的网页终端。做法跟前两格一样——一条每秒钟往日志写
一行的循环，这一次**前台**跑在 `script` 造的伪终端里，4 秒之后把伪终端关掉。

```
$ wc -l /root/amr-proof/fg.log
4 /root/amr-proof/fg.log
$ tail -1 /root/amr-proof/fg.log
fg 4 15:19:55                ← 掐断就在这一秒
```

三分钟后重连回去查，那行循环进程变成了 `[ticker.sh] <defunct>`——僵尸，意思是**已经死了、只是父进程
卡在原地没回收它**；`wc -l` 隔 3 秒量两次都还是 4 行。**伪终端一没，前台进程就停**，这句从前是常识
陈述，现在是量到的。

这一轮还量出两件附带事实，它们决定了这一章别的格子能不能往下写：

1. **同一条循环改用 `nohup ... &` 起，想做对照组，结果没测成**：连输出文件都没创建出来。原因是进程
   在"已经 fork、还没执行到 `nohup`"那一瞬间就被挂起信号打掉了——伪终端关得太快，`nohup` 还没来得及
   把"忽略挂起信号"装上。**这条不能读成"nohup 也会死"**；当时 `nohup` 能活下来的证据只有第一节那台
   机器上的 13 行涨到 21 行。**下一节把这一格补做了**：改成先确认日志已经写出 12 行再掐，`nohup`
   正常活过了断连，来源从这一个变成两个。
2. **关掉网页终端的标签页，不等于服务器侧的连接断了**：重连之后 `who` 里那个 `pts/0` 还在，
   `timeout` 和 `script` 两个进程还挂在它上面。所以"我掉线了，远端的活会不会死"这一格，
   **从厂商自带的网页终端测不出来**，得用真正的 ssh 客户端把连接掐掉再量。

## 量到的第四条：客户端掉线时，三格各自的下场

上一节那条附带事实说得很清楚：网页终端那个入口测不了"我掉线了远端会不会死"。这一格补上了——
**用真正的 ssh 客户端连进去，然后把客户端那侧的 `ssh.exe` 进程结束掉**。不碰服务器网络、不碰本机
网络配置、不拔网线：`ssh.exe` 一死，TCP 连接被重置，服务器上的 `sshd` 立刻发现会话没了。

三格各跑一遍同样的四步：起 → 确认日志已经在长 → 掐 → 等 60 秒重连读回。掐之前先做一道自检，
**`who` 里那条会话必须消失**；不消失就说明根本没断开，那一格作废。三格都过了这道自检。

| 格子               | 掐之后 60 秒读回 | 断连那 60 秒里写了几行 | 还在跑吗 | 上级进程        | 终端列  |
| ------------------ | ---------------- | ---------------------- | -------- | --------------- | ------- |
| 前台直跑           | 日志停在第 12 行 | 0 行                   | **否**   | —               | —       |
| `nohup` + `disown` | 12 行涨到 74 行  | 64 行                  | **是**   | 1               | `?`     |
| tmux 会话          | 12 行涨到 74 行  | 63 行                  | **是**   | tmux 的服务进程 | `pts/2` |

最后一行那个 `pts/2` 是重点：**不是被掐掉的那条 `pts/1`，是 tmux 自己给的一块伪终端**。
所以"活下来"不是运气——那行循环从生下来就没挂在你的连接上。

**这一格还顺手纠正了我自己一次失败的实验。** 第一轮我用 Git Bash 的 `ssh ... &` 加 `kill -9 $!`
去掐，结果三份日志全都一路涨到实验结束：`kill -9` 杀掉的是 Git Bash 里的那个壳，`ssh.exe`
根本没死，服务器从头到尾没断过连。**那一轮的"三格全活"是假的。** 换成 Windows 自己的进程管理
（`Start-Process -PassThru` 拿 PID、`Stop-Process` 结束）并加上 `who` 自检之后，才是上面这张表。
写在这里是因为这个坑跟你没关系、跟工具有关：**掐客户端的实验，必须先证明客户端真的没了。**

## 仍然没量到的那一条：真·断网

上面掐的是**客户端进程**，TCP 连接会被立刻重置，服务器当场发现。**拔掉网线、关掉 Wi-Fi、
路由器掉电这种"没有重置包"的断法，仍然没有量过。** 那种情况下 `sshd` 可能要等到自己的超时
或者 keepalive 才发现连接没了，前台进程收到挂起信号的时点会更晚——**会不会最终也死，
这一章没有证据**。想补这一条，需要两台你自己在场的机器，把其中一边的网络真的掐掉。

另外两件这一轮没做的：**每格只跑了一次**，没有重复三轮；前台那一格这次没留下僵尸进程，
而上一轮在同一台机器上量到过 `[ticker.sh] <defunct>`，差别可能出在父 shell 有没有来得及回收，
**没做对照，所以只报现象不给解释**。原始日志、进程表和自检输出在
`evidence/disconnect-three-arms-2026-10-12.md`。

## 一个顺手挖出来的负面事实

这台 Linux 实验机**不能被另一台机器连进来**：`sshd` 不在盘上（`ls` 直接报不存在），
`ss -ltnp` 的监听列表里没有 22 端口，也没有 tailscale。所以这台 Linux 实验机能当"跑命令的实验台"，
**不能当"你的第二台电脑"**。上一段写的断网实验，在这台机器上永远做不出来。
