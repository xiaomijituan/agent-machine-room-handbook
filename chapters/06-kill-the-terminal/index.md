# 第 6 章 · 终端窗口关掉了，正在跑的活会不会死

© 2026 xiaomijituan · 正文 CC BY 4.0，代码与数据 MIT · 原仓库 https://github.com/xiaomijituan/agent-machine-room-handbook

> 本章只回答一个问题：**终端窗口被关掉之后，正在运行的进程会不会因此结束。**
> 四条结论里三条是测量出来的（其中前台那条换了第二台机器才测量到），第四条写得很短，因为没有测量到。

## 关掉终端窗口时，内核发出的挂断信号

终端窗口关掉时，内核会给终端的前台进程组（在终端前台运行、结束时会一起收到信号的一组进程）发一个挂断信号，很多程序就此结束。程序要不要跟着结束，取决于上级进程（谁把这条命令生出来，术语叫父进程）是谁、进程有没有被从终端的会话里摘出去。

一句话：**进程只认上级进程是谁，不认窗口开不开。**

关键就在这一句。下面这张图要看的是每一格右边那一句——同一个终端被掐掉，三格的结果并不一样。

![三种起法各自的上级进程是谁：屏一前台直跑，进程的父亲是终端会话，窗口关掉时该终端的前台进程组会收到挂断信号，很多程序就此结束，这一格在第二台机器上测量到了——日志停在第 4 行、进程变成僵尸；屏二用 nohup 加 disown 起的进程，父进程是 1 号，原来的 shell 退出之后日志从 13 行涨到 21 行；屏三跑在 tmux 会话里的进程，宿主是 tmux 自身一个不属于任何终端的进程，伪终端被掐断之后会话仍在、日志从 6 行涨到 23 行。图底三条：关掉终端窗口打的是窗口不是进程的父亲；反过来 tmux kill-server 之后所有会话一起没了；断网的情况本章没有测](assets/three-screens-three-fathers.svg)

## 测量到的第一条：分离出去的进程活着

在一台 Linux 实验机上跑一个每秒钟往日志里写一行的循环，用 `nohup` 起、再 `disown` 把循环从当前 shell 的任务表里摘掉，然后**让启动循环的 shell 真的退出**（这台机器上每条命令都由一个独立 shell 执行、执行完就退出，所以"换一条命令"就等于换了一个 shell）。

结果：日志行数从 13 涨到 21，进程还在，`ps -ef` 显示循环进程的上级进程编号已经是 1。**这一格是第一台机器上的当场记录，逐行原始输出没有存成文件**（存了文件的是 2026-10-12 在第二台机器上做的那一轮，三格齐全，在 `evidence/disconnect-three-arms-2026-10-12.md`），所以这一格按 B 级读：能证明"当时确实看到 13 涨到 21"，不能当成随时可复现的凭证。`verify.md` 的分寸一节写着同样的话。

```
13 /data/proof/ticks.log   ← 起完之后 6 秒
21 /data/proof/ticks.log   ← 换一个 shell、再等 8 秒
root 176 1 ... sh -c for i in $(seq 1 120); do echo "tick $i ..." >> /data/proof/ticks.log; sleep 1; done
       ↑   ↑
     进程号  父进程已经是 1
```

这一条可以直接搬到你自己的机房里：**把一个长活交给 agent 时，别把长活挂在 ssh 进去所用的终端上。**

## 测量到的第二条：tmux 会话也活着，但要先确认掐断的是哪一条连接

同一台机器上建一个分离的 tmux 会话跑同样的循环，然后用一个假终端连进去看一眼，3 秒后掐断假终端（`timeout` 到点杀掉，退出码 124——**这是故意掐断，不是失败**）。

结果：会话还在（`tmux ls` 仍是同一条会话、同一个创建时间），日志从 6 行涨到 23 行；直到执行 `tmux kill-server`，会话才消失。

所以 tmux 带来的不是"进程变强了"，而是**多出一层不属于任何终端的宿主**：窗口关掉只是没有人看着 tmux 会话，宿主还在运行。真正需要小心的是反过来的那一步——执行 `kill-server` 之后，所有会话一起消失。

## 测量到的第三条：前台直跑那一格，这一轮记录到了现场

前两格在云端那台 Linux 实验机上量。**那台机器上没有 sshd、不能被连进来**，所以"关掉窗口"这一步只能用 `script` 造的伪终端（由程序模拟出来的终端设备）代替。第三格换了一台能连进来的机器：一台阿里云 ECS（CentOS 8，2 核 2G，`sshd` 在，`tmux` 没装），进出的通道是厂商自带的网页终端。做法跟前两格一样——一条每秒钟往日志写一行的循环，这一次**前台**运行在 `script` 造的伪终端里，4 秒之后把伪终端关掉。

```
$ wc -l /root/amr-proof/fg.log
4 /root/amr-proof/fg.log
$ tail -1 /root/amr-proof/fg.log
fg 4 15:19:55                ← 掐断就在这一秒
```

三分钟后重连回去查，那行循环进程变成了 `[ticker.sh] <defunct>`——僵尸，意思是**进程已经死了，父进程却卡在原地没有回收已经结束的子进程**；`wc -l` 隔 3 秒量两次都还是 4 行。**伪终端一旦消失，前台进程就会停下**，这一句从前是常识陈述，现在是测量到的。

这一轮还测量出两件附带事实，这两件附带事实决定了后面几格能不能继续写：

1. **同一条循环改用 `nohup ... &` 启动，想做对照组，结果没有测成**：连输出文件都没有创建出来。原因是进程在"已经 fork（fork 指创建子进程）、还没有执行到 `nohup`"的那一刻就被挂断信号打掉——伪终端关得太快，`nohup` 还没来得及把"忽略挂断信号"装上。**这一条不能读成"nohup 也会死"**；当时 `nohup` 能活下来的证据只有第一条结论那台 Linux 实验机上的 13 行涨到 21 行。**后面第四条结论补做了这一格**：改成先确认日志已经写出 12 行再掐，`nohup` 正常活过了断连，来源从这一个变成两个。
2. **关掉网页终端的标签页，不等于服务器侧的连接断开**：重连之后 `who` 里的 `pts/0` 仍然存在，`timeout` 和 `script` 两个进程还挂在 `pts/0` 上。所以"掉线之后远端的进程会不会死"这一格，**从厂商自带的网页终端测不出来**，需要用真正的 ssh 客户端掐断连接再量。

## 测量到的第四条：客户端掉线时，三格各自的结果

第二条附带事实已经说明：厂商自带的网页终端测不了"掉线之后远端的进程会不会死"。这一格补上了——**用真正的 ssh 客户端连进去，然后把客户端这一侧的 `ssh.exe` 进程结束掉**。不碰服务器网络、不碰本机网络配置、不拔网线：`ssh.exe` 一结束，TCP 连接被重置，服务器上的 `sshd` 立刻发现会话消失。

三格各跑一遍同样的四步：启动 → 确认日志已经在增长 → 掐断 → 等待 60 秒后重连读回。掐断之前先做一道自检，**`who` 里那条会话必须消失**；不消失就说明根本没有断开，那一格作废。三格都通过了这道自检。

| 格子               | 掐之后 60 秒读回 | 断连那 60 秒里写了几行 | 还在跑吗 | 上级进程        | 终端列  |
| ------------------ | ---------------- | ---------------------- | -------- | --------------- | ------- |
| 前台直跑           | 日志停在第 12 行 | 0 行                   | **否**   | —               | —       |
| `nohup` + `disown` | 12 行涨到 74 行  | 64 行                  | **是**   | 1               | `?`     |
| tmux 会话          | 12 行涨到 74 行  | 63 行                  | **是**   | tmux 的服务进程 | `pts/2` |

表里 tmux 那一行的 `pts/2` 是重点：**不是被掐断的那条 `pts/1`，而是 tmux 自己新建的一块伪终端**。所以"活下来"不是运气——那行循环从启动那一刻起就没有挂在你的连接上。

**第一轮实验作废，原因和原始记录如下。** 第一轮用 Git Bash 的 `ssh ... &` 加 `kill -9 $!` 去掐断，结果三份日志全都一路增长到实验结束：`kill -9` 结束的是 Git Bash 里的包装进程，`ssh.exe` 从未停止，服务器全程没有断过连。**那一轮"三格全活"的结果作废。** 换成 Windows 自身的进程管理（`Start-Process -PassThru` 取 PID、`Stop-Process` 结束）并加上 `who` 自检之后，才得到上面这张表。写在这里是因为这一条与你的操作无关，是工具的性质：**掐断客户端的实验，必须先证明客户端真的已经结束。**

## 仍然没有测量到的那一条：真·断网

上面掐断的是**客户端进程**，TCP 连接会被立即重置，服务器当场发现。**拔掉网线、关掉 Wi-Fi、路由器掉电这类"不发重置包"的断法，仍然没有测量过。** 那种情况下 `sshd` 可能要等到自身的超时或者 keepalive 才发现连接消失，前台进程收到挂断信号的时点会更晚——**会不会最终也停下来，目前还没有证据**。想补这一条，需要在场的两台机器，把其中一边的网络真的掐掉。

另外两件这一轮没有做的：**每格只跑了一次**，没有重复三轮；前台那一格这一次没有留下僵尸进程，而上一轮在同一台机器上测量到过 `[ticker.sh] <defunct>`，差别可能出在父 shell 有没有来得及回收，**没有做对照，所以只报现象、不给解释**。原始日志、进程表和自检输出在 `evidence/disconnect-three-arms-2026-10-12.md`。

## 另外一条负面事实

这台 Linux 实验机**不能被另一台机器连进来**：`sshd` 不在盘上（`ls` 直接报不存在），`ss -ltnp` 的监听列表里没有 22 端口，也没有 tailscale。所以这台 Linux 实验机能当作"跑命令的实验台"，**不能当作"你的第二台电脑"**。真·断网那一格的实验，在这台机器上永远做不出来。
