# 第 6 章 · 终端窗口关掉了，正在跑的活会不会死

© 2026 xiaomijituan · 正文 CC BY 4.0，代码与数据 MIT · 原仓库 https://github.com/xiaomijituan/agent-machine-room-handbook

> 这一章只回答一个问题：**你关掉的终端窗口，到底是不是进程的命根子。**
> 三条结论里两条是量出来的，第三条写得很短，因为没量到。

## 先说清楚"关掉终端"关掉了什么

终端窗口关掉时，内核会给终端的前台进程组发一个挂起信号，很多程序就此结束。
程序要不要跟着死，取决于进程的父亲是谁、进程有没有被从终端的会话里摘出去。

一句话记法：**进程认的是"我爹是谁"，不认"窗口开不开"。**

这一章的关键就一句话：进程只认父亲是谁，不认窗口开不开。下面这张图要看的是每一格右边那一句——
同一个终端被掐掉，三格的结果并不一样。

## 量到的第一条：分离出去的进程活着

在一台 Linux 实验机上跑一个每秒钟往日志里写一行的循环，用 `nohup` 起、再 `disown` 把循环
从当前 shell 的任务表里摘掉，然后**让启动循环的 shell 真的退出**（这台机器上每条命令都由一个
独立 shell 执行、执行完就退出，所以"换一条命令"就等于换了一个 shell）。

结果：日志行数从 13 涨到 21，进程还在，`ps -ef` 显示循环进程的上级进程编号已经是 1。

```
13 /data/proof/ticks.log   ← 起完之后 6 秒
21 /data/proof/ticks.log   ← 换一个 shell、再等 8 秒
root 176 1 ... sh -c for i in $(seq 1 120); do echo "tick $i ..." >> /data/proof/ticks.log; sleep 1; done
       ↑   ↑
     进程号  父进程已经是 1
```

这条可以直接搬到你自己的机房里：**把一个长活交给 agent 时，别把长活挂在你 ssh 进去的终端上。**

## 量到的第二条：tmux 会话也活着，但要看清你是掐断了谁

同一台机器上建一个分离的 tmux 会话跑同样的循环，然后用一个假终端连进去看一眼，3 秒后掐断假终端
（`timeout` 到点杀掉，退出码 124——**这是故意掐断，不是失败**）。

结果：会话还在（`tmux ls` 仍是同一条会话、同一个创建时间），日志从 6 行涨到 23 行；
直到我主动执行 `tmux kill-server`，会话才消失。

所以 tmux 给你的不是"进程变强了"，是**多了一层不属于任何终端的宿主**：窗口关掉只是没人看着
tmux 会话，宿主还在跑。你真正需要小心的是反过来的那一步——`kill-server` 一下，所有会话一起没了。

## 没量到的那一条：真的断网

**断网实验在这台机器上做不到，做得到就等于把取证环境自己杀掉。** 取证环境是一个 Kubernetes 容器，
断网会让连接、取证和回传一起消失，所以这一轮只做了不伤害连通性的观察（网卡状态、收发计数）。

结论就只能到这里：**断掉的到底是不是"你和新机器之间的那条线"，这一章没有证据**。
想补这一条，需要两台你自己在场的机器，把其中一边的网络真的拔掉，看另一边的进程还写不写日志。
我没有替你写这条结论，因为没人量过。

## 一个顺手挖出来的负面事实

这台 Linux 实验机**不能被另一台机器连进来**：`sshd` 不在盘上（`ls` 直接报不存在），
`ss -ltnp` 的监听列表里没有 22 端口，也没有 tailscale。所以这台 Linux 实验机能当"跑命令的实验台"，
**不能当"你的第二台电脑"**。上一段写的断网实验，在这台机器上永远做不出来。
