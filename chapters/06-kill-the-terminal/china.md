# 第 6 章 · 国内网络环境下的差异卡片

| 命令                                              | 你会看到什么                  | 坑在哪                                                                                                                   |
| ------------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `ssh 家里的机器` 后前台跑长活，然后关掉笔记本盖子 | 进程随会话结束而死            | 真正致命的是"进程挂在你这条 ssh 会话上"，不是网络慢；国内跨网掉线更频繁，所以这个坑更容易踩到                            |
| `nohup 长活 & disown`                             | 换个 shell 上去看，日志还在涨 | 日志要写到文件里；只写到标准输出而你没重定向，进程活着你也看不到                                                         |
| `tmux new -d` 之后 `tmux attach` 再掐断           | 会话还在                      | 别把 `timeout` 的退出码 124 读成失败；也别顺手敲 `tmux kill-server`，那是一下子杀掉所有会话                              |
| 从云厂商控制台"重启网络"或换 IP 后再连回 tmux     | 取决于对端地址还认不认        | 家里宽带的入站常被运营商挡掉，这时该用的是虚拟局域网那一层，见第 2 章                                                    |
| 用云厂商的网页终端登录后，直接关掉那个标签页      | 服务器侧的会话往往还在        | `who` 里那个 `pts` 仍然列着、挂在它上面的进程没被杀。别把"关了网页标签"当成断连实验——要测掉线得用真 ssh 客户端把连接掐掉 |

一句提醒：第一台取证用的 Linux 实验机**没有 sshd、也没有 tailscale**，能证明的是"进程存活"，
证明不了"跨机器连得回来"；前台那一格是在第二台机器（一台能连进来的阿里云 ECS，CentOS 8，
**没装 tmux**）上补量的，所以 tmux 那两条结论目前只有第一台机器一个来源。国内那部分的可连性问题在
第 2 章里量过，本章不重复结论。
