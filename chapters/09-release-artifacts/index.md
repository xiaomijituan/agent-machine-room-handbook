# 第 9 章 · 发版：把"我做完了"变成别人能跑的那一个文件

© 2026 xiaomijituan · 正文 CC BY 4.0，代码与数据 MIT · 原仓库 https://github.com/xiaomijituan/agent-machine-room-handbook

> 第 8 章讲的是别人（和机器）凭什么相信提交的代码；第 9 章讲下一步：**把你做出来的东西变成另一个人不读源码就能用的那几份文件**。本章的每个数字都是从发布页和本机 Git 记录里读出来的，包括一个我自己写错又改回来的数字。

## 发版发出的是三份文件

**发版**：给一组文件贴上一个版本号，放到别人能下载到的地方，然后**假设发出去的文件永远收不回来**。本手册依赖的仓库（聚变 / fusion）从 `v0.1.0` 起固定发三份：

```
fusion-sim-<版本>.html   离线单文件模拟器：双击就起机房，不联网取任何东西
scenario-check.mjs       剧本校验器：判断一份剧本合不合格，点出是哪个字段
review-cli.mjs           投影器：把一局的事件流变成一张决策表
```

`v0.1.2` 那次发布页上读到的真实清单（2026-10-10 从 GitHub 的发布接口取的）：

| 文件                    |    字节 | 下载次数 |
| ----------------------- | ------: | -------: |
| `fusion-sim-0.1.2.html` | 404,823 |        1 |
| `review-cli.mjs`        |   8,933 |       12 |
| `scenario-check.mjs`    | 138,590 |       12 |

**下载次数这一列最诚实**：两个命令行工具各被下载 12 次，因为本手册的 CI 每跑一次就下载一次；那个 40 万字的单文件 HTML 只被下载过 1 次——就是我自己下载回来核对字节和校验和的那一次。**看下载数就知道谁在真正消费哪个产物**，不需要猜。

整章的关键就一句话：发版是一条单向路，文件发出去就收不回来。下面这张图要看第③步和第④步两格：第③步发生在别人的机器上，第④步要把产物下载回你自己的机器再跑一遍，缺任何一步都不算发完。

![发版是一条单向路，四步从上到下：第一步在你自己的机器上打出三份文件，版本号只有一个源头 APP_VERSION 等于 0.1.2；第二步发布页，三份资产挂上 v0.1.2，真实字节是 404,823、8,933、138,590；第三步别人家的 CI，一条 curl 下载就用，只下载产物不读源码，下载次数 12；第四步你自己，下载回来核字节与校验和，再拿那份跑一遍。图底三条：发出去的东西改不了、能挪的只有标签；v0.1.2 的标签指向一个只改文档的提交，目的是让文档里的字节数跟产物一致；先构建、再量、最后写文档——404,476 是第一次修复后的数、重打之后是 404,823，而第三方撤回与删资产后下游怎么失败本章未测](assets/release-pipeline.svg)

## 版本号只写在一处

聚变仓库里的版本号文件（`src/lib/version.ts`）全文只有三行有效内容：

```ts
/**
 * The app's own version, written in exactly one place: the event stream header, the bundled
 * release artifacts (ADR-0008) and the git tag they ship under must all say the same number.
 */
export const APP_VERSION = "0.1.2";
```

注释把要求写得很明确：**标签、产物文件名、每一局导出的事件流头部，三处必须是同一个版本号**。写三遍的代价不是麻烦，而是这三处会在某一天各说各话——"各说各话"在用户那边表现为"我按文档下载了 0.1.2，跑出来的行为跟文档不一样"。

本手册仓库也照同样的思路加了一道检查：`vendor/` 里那份复制件的版本、章节页引用的文件名、CI 配置里固定写明的 `FUSION_TAG`，**三处必须是同一个版本号**。`scripts/check.mjs` 会核对这三处，不一致就让检查变红。这道检查做过反向验证：把 `FUSION_TAG` 改回 `v0.1.1`，`npm run check` 退出码 1。

## 一个我自己写错的数字

发 `v0.1.2` 之前，我在设计记录里写"单文件模拟器实测 **404,476** 字节"。404,476 这个数字当时确实测量过——不过测量的是**第一次修复之后**打出的那份单文件模拟器；第二条修复又往打包结果里加了代码，重打之后是 **404,823**。如果照第一个数字发出去，标签指向的那棵提交树上，文档写着另一个数。

于是有了这条规矩：**先构建，再量，最后写文档**——顺序反了，写进文档的就是一个当时正确、随后过期的数字。

紧接着的一步是让"文档里的数字"和"产物的字节"对上：我把 `v0.1.2` 这个标签**挪了一次**，挪到一个只改文档的提交上。本机 Git 读出来的原文：

```
$ git for-each-ref refs/tags/v0.1.2 --format='%(objectname:short) → %(objecttype) → %(*objectname:short)'
dff5f4e → tag → 640eb9a

$ git log -1 --format='%s' 640eb9a
docs: 单文件模拟器的字节数按重打之后的实测改
```

读法：`v0.1.2` 是一个**附注标签**（tag 对象 `dff5f4e`），标签指向的提交 `640eb9a` 只改了文档。也就是说，**`v0.1.2` 这个版本的标签停在"只改说明"的提交上**，而产物是在这个提交对应的文件树上重打出来的。

同时测量到的还有一条事实：**同一棵提交树上只改文档，重打出来的单文件 HTML 校验和完全不变**（`v0.1.2` 那份是 `d13741a3…`）。原因是文档不进打包结果。所以"改了文档要不要重发产物"，答案取决于修改的内容会不会被打包进产物——**不要猜，算一次校验和**。

## 已发布的文件不可更改，标签可以挪动：两件不同的事

| 动作                       | 能不能做 | 原因                                                                         |
| -------------------------- | -------- | ---------------------------------------------------------------------------- |
| 挪一个还没有人消费过的标签 | 成本低   | 标签只是一个指针；挪动会在推送输出里留下记录                                 |
| 替换发布页上已经发布的文件 | 不做     | 别人可能已经下载了旧文件；替换之后"依赖 0.1.2"这句话的含义变了，用户不会察觉 |
| 发一个新版本号             | 永远可以 | 旧版本的文件仍然挂在旧标签下，依赖方自行决定是否升级                         |

`v0.1.1` 那次的处理方式是：独立审查出来的四条修复改变了产物的对外行为，**没有直接替换 `v0.1.0` 已经发布的文件**，而是发新版本，并在记录里写清"依赖 `0.1.1` 或者之后最新的 `0.1.x`"。

## 退出码也是对外契约

两个命令行工具被下游 CI 使用，靠的不是"输出好看"，而是**退出码可断言**。契约原文如下表：

| 产物                 | 用法                                                       | 退出码                                                                 |
| -------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------- |
| `scenario-check.mjs` | `node scenario-check.mjs <a.json> [<b.json> …] [--strict]` | 0 = 全部合法；1 = 有内容错误；2 = 用法错（一个文件都没给）或文件读不到 |
| `review-cli.mjs`     | `node review-cli.mjs <run.jsonl> [--json]`                 | 0 = 排出来了；1 = 这份文件不是合法事件流；2 = 用法错或文件读不到       |

**1 和 2 不能混**：1 是"你交的东西不合格"，2 是"工具自己没跑成"。下游 CI 要写出"内容不合格就红、环境没跑成也红但原因不同"的断言，全靠这条分界。`--strict` 只把警告升级成 1，`--json` 只换输出形态，都不改退出码。

## 发完之后还要下载回来复验

这一步是本仓库真实做过的，顺序如下（`v0.1.2` 那次）：

1. 从发布页**下载**那三份文件；
2. 比对字节与 MD5（一种校验和算法）：下载回来的 `fusion-sim-0.1.2.html` 是 404,823 字节、`d13741a3…`，与本地构建产物逐字节一致；
3. **用下载回来的那两份命令行工具**真跑一遍：拿 `scenario-check.mjs` 校验每一章剧本、拿 `review-cli.mjs` 投影每一章的运行记录，核对退出码和报错文案是否与文档一致。

第 3 步不是走形式：`v0.1.2` 的两处报错文案修复（哪个字段多写了、被拒的主机不再被说成"不存在"），只有在**用发布出去的那份跑**的时候才算验过——在源码仓库里跑单测，验的是另一份代码。

## 不发 npm 包的三条理由

看起来的"标准做法"是把校验器发成 npm 包。仓库的设计记录里写明了三条拒绝理由：要占用包名、要跟聚变自身的发布节奏解耦、在中国大陆安装还要等 npmmirror（国内镜像站）同步。发布页附单文件产物是零安装、一条 `curl` 就能取到的最小方案；日后真需要复用到别处时再补发 npm，两件事不冲突。

另一条相关的取舍是**兼容窗口**（下游落后于上游时仍能正常配合的版本范围）：下游可以比上游落后一个大版本仍然不出错——剧本格式接受的版本号范围是 `[当前, 当前-1]`，所以手册不必跟着聚变每次发版立刻改动。

## 没有测量到的部分

1. **真有第三方依赖时能不能撤回**：那两个工具的 12 次下载全部来自我们自己的 CI。"发出去收不回来"是按原则写的，不是按一次真实的撤回事故写的。
2. **发布页资产被改名或删除之后，下游 CI 的失败表现**：没测过。复现这一项需要故意做一次删除，而那是拿公开产物做实验。
3. **别人拿到旧版本会不会自己升上来**：没有真实第三方用户，无从观察。
4. **"教别人如何核验产物"的那段话自己没跑过**——这一类错误我确实犯过一次（写过"单文件 HTML 的第 1 到 3 行写着出身版本"，`head -3` 的输出是 `<!doctype html>`、`<html lang="zh">`、`<head>`，出身注释只在两个 `.mjs` 的头两行）。**同类错误有没有第二处，没有系统扫过。**
