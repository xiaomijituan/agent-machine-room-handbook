# 第 7 章验证记录

## 机器（在哪两台机器上量的）

- 一端是家里那台 Windows 机器（本机，Windows 10 26200，x86_64），tailscale 客户端 1.102.2。
- 另一端是一台随身 Android 设备，与本机在同一个 tailnet 内。
- 两台机器的设备名、tailnet 地址、tailnet 账号在入库前都按格式替换掉了（见"涂改"一节）。

## 版本（跑的是什么版本）

- Tailscale 1.102.2；探测命令 `tailscale ping -c N`，状态命令 `tailscale status`。
- 中继标识读自输出里的 `DERP(tok)` 与 `relay "tok"`，本章不解释这个代号代表哪个机房所在城市。
- 模拟器：fusion `0.1.2`；剧本 `amr-ch07-two-machines-one-tailnet` 版本 `0.1`。

## 测到了什么（等级 A，本环境可复现）

| 结论                                                       | 依据                                                                                                                      |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 跨设备连通成立，且十次全部绕中继                           | `tailscale ping -c 10` 十个 pong，每行都是 `via DERP(tok)`，末尾 `direct connection not established`                      |
| 延迟区间 339–485 毫秒，首包 2.629 秒                       | 同一批输出的逐包延迟                                                                                                      |
| 对端状态是"活跃但走中继"                                   | `tailscale status` 里那条对端显示 `active; relay "tok"`                                                                   |
| 断 20 秒或 25 秒再拉起，恢复后的第一发没有一次是正常毫秒级 | 三轮 `tailscale ping -c 3` 各自的第一发：1.353 秒、直接超时、3.367 秒；后面几发有 461/388 毫秒，也有 4.882 秒与再一次超时 |
| 超时出现过，但不是每轮都有                                 | 中间那一轮三次里两行 `timed out`、一行 4.882 秒；另外两轮三次全部返回 pong，所以"必然有几次不通"这条正文里没写            |
| 云端 Linux 实验机不能被连进来                              | 无 `sshd`、监听端口无 22、无 tailscale、`/proc/1/cgroup` 显示容器形态                                                     |

## 没测到什么

1. **为什么打洞失败**：没有抓 STUN 行为、没做端口映射观测、没换一条宽带做对比。正文只报"全走中继"这个现象。
2. **换到别的网络会不会变成直连**：只在家里的出口和手机蜂窝这两组条件下量过，没有系统对比。
3. **对端断网时，对端自己跑的活会不会死**：本轮只掐了本机的虚拟网卡。顺带量到本机那个每 2 秒
   写一行的分离进程在这 25 秒里没停（6 行涨到 26 行，再等 10 秒涨到 35 行）——这条几乎必然成立，
   **不能拿它冒充"agent 的活在断网后还活着"**，那个实验要掐对端的网。
4. **配图画到哪为止**：`assets/two-machines-relay-and-reconnect.svg` 只画上面两组等级 A 的输出，
   打洞失败的原因没有证据，图里同样没画。**配图本身的可读性没有实测**：没有请读者只看图复述结论，
   也没在不同屏幕宽度下验过。
5. 中继所在国家/城市的名字不写，只写代号 `tok`：正文的结论不依赖它。
6. **重连之后"必然有几次不通"**：三轮里只有一轮出现 `timed out`，另外两轮三发全部返回 pong，
   所以"必然不通"写不成结论。正文现在的说法是"每一轮都有秒级的 pong，超时会出现但不是每轮都有"。
7. **第二轮结尾那一行**：取证时每条命令只留输出末尾四行，`-c 3` 最多三行结果，探测行没被丢掉；
   但第二轮那四行里没有 `direct connection not established`，所以那一轮不引用"直连没建立"。

## 等级（每条结论的可信度）

- A（本机可复现）：上面表格里的六条全部。
- B（模拟器里真跑，点击由脚本合成、导出未落盘）：`reference.jsonl` 那一局。
- C（他人报告）：无。
- D（推断）：无——"常见解释是运营商级地址复用"那句在正文里明确写成没有证据，不给等级。

## 涂改（入库前改掉了什么）

- 两台机器的设备名替换为 `<本机名>`、`<对端设备名>`；两个 tailnet IPv4 与 IPv6 地址替换为
  `<tailnet-IP>`；tailnet 账号邮箱替换为 `<tailnet 账号>`；对端地址在命令示例里写作 `<对端地址>`。
- 自查方式：按格式扫一遍残留（`100.x.x.x`、设备名、账号），确认为零命中后才留档。
- 探测输出中的延迟数字与 `via` 字段一字未改；空输出与超时行原样保留。
- **一处自己写错的记录（2026-10-09 改）**：正文原先把三轮输出拼成一条"断 25 秒、头两次超时、
  第三次 3.367 秒才通"的转录，并按这个说法写了结论"头两秒必然不通"。三轮实际各是各的数：
  两轮三次全部返回、一轮出现两行超时。现在正文按三轮分开贴，结论改成"恢复后的第一发没有一次是
  正常毫秒级"，"必然不通"移进上面的"没测到什么"。另外三轮都是在拉起虚拟网卡之后等 12 到 18 秒
  才发探测，所以正文里"立刻重测"那句也改成了等待时长。
- `reference.jsonl` 的事件行取自模拟器 sessionStorage 里真跑的一局（运行号 `rmv0lp3z5-13y3v8a`、
  种子 `2415468250`、`appVersion 0.1.2` 都是那局自己的值），header 的 `snapshot` 按同一次运行重建。
