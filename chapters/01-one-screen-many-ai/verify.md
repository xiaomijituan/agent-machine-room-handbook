## 怎么测的

沙箱是另一个 AI 在跑，我碰不到它。所以走**提示词往返**：我写一段把要跑的命令、要采集的输出、要交付的文件全部锁死的提示词；作者贴过去执行；那边产出一个证据文件下载回来。三轮的原文都在本目录 `evidence/` 下：

- `tmux-evidence.md` — 基础行为（会话、进程、分屏、关服务器）
- `tmux-evidence-part2.md` — 试图测"离开再回来"，**失败**（沙箱没有真终端）
- `tmux-evidence-part3.md` — 用 `script` 造伪终端 + `timeout` 掐断，**成功**，拿到对照

## 一个必须说明的模拟

我们**没有真的去点掉一个终端窗口**。用的是 `timeout 3 script -qec '...' /dev/null`：`script` 造一个假终端，`timeout` 三秒后把它掐死（退出码 `124` 就是"被 timeout 杀掉"的记号）。

这对不对？**对**，但只在一种意义上：真实场景里你关掉终端窗口，系统会给那个窗口里的进程发一个"挂断"信号，进程被带走。`timeout` 掐掉伪终端造成的就是这个结果。所以书里要写成"我们模拟了关掉终端窗口"，不能写成"我们关掉了终端窗口"。

## 证明了什么

1. **放进 tmux 会话里的活，你关掉终端它照跑。**
   掐断伪终端后：`tmux ls` 里 `desk5` 还在；日志 6 行 → 等 5 秒 → 11 行；`ps` 里两条进程都活着，父进程是 1 号。
   证据：`evidence/tmux-evidence-part3.md` 第 2 节。

2. **同样的掐断，不在 tmux 里的活就死了。**
   日志卡在 3 行，5 秒后还是 3 行，`ps` 查不到进程。
   证据：同上第 3R 节。**这一条和第 1 条是同一套工具、同一个掐断方式得到的相反结果**——这才是对照，不是猜的。

3. **"杀掉会话"才会真的杀掉进程。**
   `tmux kill-session` 之前两条进程在，之后一条不剩；而且会话里那句 `echo DONE > /data/desk1-done.txt` 从未执行（文件不存在），说明整条命令链被一起掐死了。
   证据：`evidence/tmux-evidence.md` 第 3 节、`evidence/tmux-evidence-part2.md` 第 2 节（两次独立复现）。

4. **一块屏幕能切成好几块，每个 AI 占一块。**
   `tmux list-panes -a` 先列出 4 个 pane，`split-window` 之后 `ai-b` 变成 0 号与 1 号两块。
   证据：`evidence/tmux-evidence.md` 第 5 节。

5. **attach（回来）这一步必须有真终端。**
   在没有终端的环境里，`tmux attach` 直接报 `open terminal failed: not a terminal`；`detach-client` 报 `can't find client`。
   证据：`evidence/tmux-evidence-part2.md` 第 1.2 节。**这条是意外收获**：它告诉读者，在脚本、CI、沙箱这类自动化环境里，你只能用 `tmux ls`、`tmux capture-pane` 这类命令看状态，别指望能"连上去看"。

6. **`tmux kill-server` 之后会留下僵尸进程。**
   `ps` 里出现两个 `[tmux: server] <defunct>`。
   证据：`evidence/tmux-evidence.md` 第 5.2 节。

## 没证明什么（诚实记录）

- **没证明"关掉终端窗口一定会带走普通后台任务"** 这句话本身。反倒有一次实测显示：在这种"每条命令都起一个独立 shell"的环境里，一个用 `&` 丢到后台的任务**活了下来**，父进程变成 1 号（`evidence/tmux-evidence-part2.md` 第 3 节）。原因是不在那个环境里根本没有"终端窗口"这个东西可以关。所以书里要说清楚：**"放到后台"和"放进 tmux"解决的不是同一个问题**——前者管"我这会儿不想看着它"，后者管"我的终端没了它还得活着"。
- **没在 Windows 上测过任何一步。** 作者那台机器没有 tmux、没有 Linux 子系统。书里 Windows 的部分只能写"装不了，怎么办"，见 `china.md`。
- **没测多用户、没测 tmux 配置文件（`~/.tmux.conf`）、没测鼠标与快捷键的实际手感。** 这些不在本章承诺范围内，别在书里顺嘴提。
- **没测过配图本身。** `assets/one-screen-per-agent.svg` 是示意图，不是屏幕实拍：图里每个元素都取自本章正文和 `scenario.json` 已经写明的东西（三块屏各跑 claude / codex / opencode、codex 那块卡在等回答、你只在拍板时出现），图上没有新增任何实测结论。

## 一次失败也是证据

对照组第一次跑出来是语法报错：

```
bash: -c: line 2: syntax error near unexpected token `2'
```

原因是 `$(seq 1 60)` 被 `script` 内部那层 shell **提前展开**了，传下去的命令已经不是原样。沙箱那边自己诊断出来，把 `$` 转义成 `\$` 重跑，才拿到第 3R 节那组干净数据。

这件事对读者有用：**只要命令里带 `$(...)`，穿过 `script`、`ssh`、`tmux new -d` 这类会再过一层 shell 的地方，就要考虑它在哪一层被展开。**书里会把这个报错原文贴出来。

## 这一局的记录是怎么来的（`reference.jsonl`）

不是手写的，是模拟器自己记的。过程如实记在这里：

1. 本地把模拟器跑起来（`npm run dev -- --port 5273`）。
2. 用浏览器自动化操作：导入本章 `scenario.json` → 进机房 → 拍板一次（选"让它加等待再重跑"）→ 下发一句话任务给空闲那块屏。
3. **点的是应用自己的按钮，跑的是应用自己的事件处理函数**，但触发方式是脚本合成的，不是人手点的。
4. 点了"导出这一局"，但**下载没有落到磁盘**（Qoder 的内嵌浏览器把下载拦在自己那一层，几个常见下载目录里找不到文件）。所以这份 `reference.jsonl` 的内容取自应用写在 `sessionStorage["fusion.run"]` 里的那一份记录——同一段代码产出的数据。
5. 末尾那行 `run.end{reason:"export"}` 是按应用自己的收尾规则在页面里补的（应用导出未闭合的局时也补这一行）。

**这一局里有什么**：6 个事件、**两次决策**（一次拍板 `add-wait`、一次下发 dispatch）。**没有**"杀掉会话"那种决策，所以正文里不提它。

**一个顺带查明的事，值得写进书里**：浏览器把不可见标签页的定时器限速了。这一局跑了约 3 分钟，页面里的 tick 计数 `n` 只走到 6（正常应该一秒一拍）。也就是说**把模拟器挂在后台标签页，它是几乎不动的**。读者一定会撞上，书里要提前说。

## 证据等级

**A 级**（本机上真实执行、有原始输出、有失败记录、可复现）。但限定范围：**在 Ubuntu 22.04 + tmux 3.2a + root + 云端沙箱**这个组合下。读者在自己的 Linux/macOS 上应当能复现同样结果；Windows 用户需要先有一个 Linux 环境。

`reference.jsonl` 单独定级：**B 级**——数据是应用真产出的，但采集方式有上述两点保留（合成点击、下载未落盘）。
