## 测量方式

沙箱由另一个 AI 在跑，我们碰不到沙箱本身。所以走**提示词往返**：我们写一段把要跑的命令、要采集的输出、要交付的文件全部锁死的提示词；作者贴过去执行；那边产出一个证据文件下载回来。三轮的原文都在本目录 `evidence/` 下：

- `tmux-evidence.md` — 基础行为（会话、进程、分屏、关服务器）
- `tmux-evidence-part2.md` — 试图测"离开再回来"，**失败**（沙箱没有真终端）
- `tmux-evidence-part3.md` — 用 `script` 造伪终端 + `timeout` 掐断，**成功**，拿到对照

## 一个必须说明的模拟

我们**没有真的去点掉一个终端窗口**。用的是 `timeout 3 script -qec '...' /dev/null`：`script` 造一个假终端，`timeout` 三秒后把假终端掐掉（退出码 `124` 就是"被 timeout 杀掉"的记号）。

用伪终端替代真窗口的做法是否成立？**成立，但只在一个意义上**：真实场景里你关掉终端窗口，系统会向窗口里的进程发一个"挂断"信号，进程被带走。`timeout` 掐掉伪终端造成的正是这一效果。所以书里要写成"我们模拟了关掉终端窗口"，不能写成"我们关掉了终端窗口"。

## 已经证明的结论

1. **放进 tmux 会话里的活，你关掉终端之后照常运行。**
   掐断伪终端后：`tmux ls` 里 `desk5` 还在；日志 6 行 → 等 5 秒 → 11 行；`ps` 里两条进程都活着，父进程是 1 号。
   证据：`evidence/tmux-evidence-part3.md` 第 2 节。

2. **同样的掐断，不在 tmux 里的活就死了。**
   日志卡在 3 行，5 秒后还是 3 行，`ps` 查不到进程。
   证据：同上第 3R 节。**这一条和第 1 条是同一套工具、同一个掐断方式得到的相反结果**——这才是对照，不是猜的。

3. **"杀掉会话"才会真的杀掉进程。**
   `tmux kill-session` 之前两条进程在，之后一条不剩；而且会话里那句 `echo DONE > /data/desk1-done.txt` 从未执行（文件不存在），说明整条命令链被一起掐死了。
   证据：`evidence/tmux-evidence.md` 第 3 节、`evidence/tmux-evidence-part2.md` 第 2 节（两次独立复现）。

4. **一块屏幕能切成好几块，每个 AI 占一块。**
   `tmux list-panes -a` 先列出 4 个 pane，`split-window` 之后 `ai-b` 变成 0 号与 1 号两块。
   证据：`evidence/tmux-evidence.md` 第 5 节。

5. **attach（回来）这一步必须有真终端。**
   在没有终端的环境里，`tmux attach` 直接报 `open terminal failed: not a terminal`；`detach-client` 报 `can't find client`。
   证据：`evidence/tmux-evidence-part2.md` 第 1.2 节。**这条是意外收获**：在脚本、CI、沙箱这类自动化环境里，只能用 `tmux ls`、`tmux capture-pane` 这类命令看状态，无法接入屏幕。

6. **`tmux kill-server` 之后会留下僵尸进程。**
   `ps` 里出现两个 `[tmux: server] <defunct>`。
   证据：`evidence/tmux-evidence.md` 第 5.2 节。

## 未证明的部分（诚实记录）

- **没有证明"关掉终端窗口一定会带走普通后台任务"这句话本身。** 反倒有一次实测显示：在一个"每条命令都起一个独立 shell"的环境里，一个用 `&` 丢到后台的任务**活了下来**，父进程变成 1 号（`evidence/tmux-evidence-part2.md` 第 3 节）。原因是那个环境里根本没有可以关闭的"终端窗口"。所以书里要说清楚：**"放到后台"和"放进 tmux"解决的不是同一个问题**——`&` 管的是"我这会儿不想盯着这条命令"，tmux 管的是"终端没了，命令还得活着"。
- **Windows 侧在 2026-10-14 补测了一部分，另一部分仍然没测。** 已经测量到的（作者本机，Windows 10.0.26200，Git Bash 的 bash 是 `4.4.23(1)-release (x86_64-pc-msys)`，`uname -s` 返回 `MINGW64_NT-10.0-26200`）：`command -v tmux` 返回空、退出码 1；`command -v script` 返回空；`ls -d /dev/pts` 报 `No such file or directory`；`/usr/bin/winpty` 与 `winpty-agent.exe` 在场。**仍然没测的**：Git Bash 能不能靠 `winpty` 这一类转接层补出 tmux 需要的伪终端，以及补出来之后 tmux 能不能跑。`china.md` 里那段"装了 Git Bash 不等于有 tmux"已经按这两档改写。
- **一条探测方法的教训（写给后面复现的人）**：这台机器上 `tty`、`stty`、`python -c "sys.stdout.isatty()"` 三组探测**不能当证据使用**。原因是这些命令都通过一个把标准输出接成管道的自动化通道执行，探测读到的必然是"不是终端"；故意加一道对照——`bash -c 'tty' | cat`——输出与那三次一模一样（都是 `not a tty`）。同一个 shell 里 `sys.stdin.isatty()` 是 `True`、`sys.stdout.isatty()` 是 `False`，这正是"输出被接走"的特征；`winpty tty` 也在同一个位置失败，报 `stdin is not a tty`。**要判断某个终端本身是不是终端，探测不能经过管道**：得由人在桌面上打开那个终端窗口直接敲，或者用另一台真的伪终端做对照。
- **没测多用户、没测 tmux 配置文件（`~/.tmux.conf`）、没测鼠标与快捷键的实际手感。** 这些不在本章承诺范围内，不要随口写进正文。
- **没测过配图本身。** `assets/one-screen-per-agent.svg` 是示意图，不是屏幕实拍：图里每个元素都取自本章正文和 `scenario.json` 已经写明的东西（三块屏各跑 claude / codex / opencode、codex 那块卡在等回答、人只在拍板时出现），图上没有新增任何实测结论。

## 一次失败也是证据

对照组第一次跑出来是语法报错：

```
bash: -c: line 2: syntax error near unexpected token `2'
```

原因是 `$(seq 1 60)` 被 `script` 内部那层 shell **提前展开**了，传下去的命令已经不是原样。沙箱那边自己诊断出来，把 `$` 转义成 `\$` 重跑，才拿到第 3R 节那组干净数据。

这一点对复现这组实验的人有用：**只要命令里带 `$(...)`，穿过 `script`、`ssh`、`tmux new -d` 这类会再过一层 shell 的地方，就要考虑 `$(...)` 在哪一层被展开。**书中会附上这条报错的原文。

## 本局记录的生成方式（`reference.jsonl`）

这份记录不是手写的，是模拟器自己记的。过程如实记在这里：

1. 本地把模拟器跑起来（`npm run dev -- --port 5273`）。
2. 用浏览器自动化操作：导入本章 `scenario.json` → 进机房 → 拍板一次（选"让它加等待再重跑"）→ 下发一句话任务给空闲那块屏。
3. **点的是应用自己的按钮，跑的是应用自己的事件处理函数**，但触发方式是脚本合成的，不是人手点的。
4. 点了"导出这一局"，但**下载没有落到磁盘**（下载被 Qoder 的内嵌浏览器自己接住，没写到磁盘上，几个常见下载目录里找不到文件）。所以这份 `reference.jsonl` 的内容取自应用写在 `sessionStorage["fusion.run"]` 里的那一份记录——同一段代码产出的数据。
5. 末尾那行 `run.end{reason:"export"}` 是按应用自己的收尾规则在页面里补的（应用导出未闭合的局时也补这一行）。

**这一局里有什么**：6 个事件、**两次决策**（一次拍板 `add-wait`、一次下发 dispatch）。**没有**"杀掉会话"类决策，所以正文里不涉及这类内容。

**一个顺带查明的事，值得写进书里**：浏览器把不可见标签页的定时器限速了。这一局跑了约 3 分钟，页面里的 tick 计数 `n` 只走到 6（正常应该一秒一拍）。也就是说**把模拟器挂在后台标签页，模拟器几乎不推进**。正文要提前说明这一现象。
